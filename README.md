# TripFund

TripFund собирает токены ERC-20 на поездку. При создании контракта задаются организатор, цель сбора и дедлайн. До дедлайна участники вносят токены. После срока возможен один из двух исходов:

- Если цель достигнута, организатор один раз вызывает `withdraw()` и получает сумму взносов.
- Если собранная сумма ниже цели, каждый участник вызывает `refund()` и возвращает свой вклад.

Контракт находится в `src/TripFund.sol`, тесты в `test/TripFund.t.sol`.

## Параметры при создании

| Параметр | Значение |
| --- | --- |
| `token_` | Адрес токена ERC-20, в котором проходит сбор |
| `organizer_` | Адрес организатора, которому доступны средства при успешном сборе |
| `goal_` | Цель сбора в минимальных единицах токена, больше нуля |
| `deadline_` | Время окончания сбора в секундах Unix; должно быть в будущем |

Для токена и организатора указываются ненулевые адреса.

## Как внести токены

Для взноса контракту TripFund нужно разрешение на списание токенов. Если текущего разрешения недостаточно, участник отправляет со своего адреса две транзакции в таком порядке:

```text
1. В токене ERC-20: approve(адрес TripFund, amount)
2. В TripFund:     contribute(amount)
```

Если разрешение уже покрывает `amount`, первый шаг можно пропустить. `contribute` переводит токены в контракт и записывает вклад за адресом отправителя. Один адрес может внести токены несколько раз. `amount` указывается в минимальных единицах: для токена с 18 знаками после запятой 10 токенов записываются как `10e18`.

Взносы принимаются до дедлайна. После него только организатор вызывает `withdraw()` при достигнутой цели. Если собранная сумма ниже цели, участник возвращает весь свой вклад одним вызовом `refund()`.

`totalRaised` хранит общую сумму принятых взносов; после возвратов значение сохраняется. Цель сбора и функции `withdraw()` и `refund()` учитывают взносы, записанные через `contribute()`. При прямом переводе токены остаются на адресе TripFund.

## Установка и проверка

Нужен установленный Foundry с командой `forge`. Проект проверен с Forge 1.8.6 и компилятором Solidity 0.8.24; в контракте указано `pragma solidity ^0.8.20`. Зависимости: OpenZeppelin Contracts 5.0.2 и forge-std 1.17.0.

```sh
git clone --recurse-submodules https://github.com/arseniytitarenko/hse-web3-hw2.git
cd hse-web3-hw2
forge build
forge test
```

Если репозиторий уже склонирован без зависимостей, загрузите их командой `git submodule update --init --recursive`.

Тесты проверяют взносы, права организатора, достижение цели, границу дедлайна, независимые возвраты, повторные вызовы, события и прямые переводы токенов.

## Бонус: обновление через прокси

`src/TripFundV1.sol` хранит параметры сбора и взносы в хранилище прокси. При создании прозрачного прокси вызывается `initialize()`. Инициализация прокси выполняется один раз. В реализации инициализаторы заблокированы. Обновить реализацию может владелец `ProxyAdmin`.

`src/TripFundV2.sol` добавляет `contributeFor(beneficiary, amount)`: отправитель платит токены, а право на возврат получает `beneficiary`. Адрес прокси и накопленные данные при обновлении сохраняются. Эти сценарии проверяются в `test/TripFundProxy.t.sol`.

Совместимость хранилища V1 и V2 проверяется OpenZeppelin Upgrades CLI. Для команды нужны Node.js и pnpm:

```sh
pnpm install
forge build --force
pnpm run validate:upgrade
```

Команда сравнивает V2 с V1 и завершается с `SUCCESS`, если обновление безопасно для хранилища.
